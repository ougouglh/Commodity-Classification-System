# 关于商品画像信息准确性的说明

## 问题描述

近期有用户反馈，系统输出的商品画像存在"瞎编"信息的情况，例如：

❌ **错误示例**：
```json
{
  "product_name": "农夫山泉NFC橙汁1L",
  "flavor": "橙汁味",        // 可能是瞎编
  "packaging": "纸盒",       // 可能是瞎编
  "sugar_content": "含糖",   // 可能是瞎编
  "origin": "全国",          // 明显瞎编！
  "confidence": 0.92
}
```

✅ **正确示例（修复后）**：
```json
{
  "product_name": "农夫山泉NFC橙汁1L",
  "category": {
    "level_1": "食品",
    "level_2": "饮料",
    "level_3": "果汁饮料",
    "level_4": "NFC果汁"
  },
  "flavor": "橙汁味",        // 合理（商品名称中包含"橙汁"）
  "packaging": "未知",        // 诚实（知识库未明确标注）
  "sugar_content": "未知",   // 诚实（知识库未明确标注）
  "brand": "农夫山泉",       // 合理（商品名称中包含）
  "function": "未知",        // 诚实（知识库未明确描述）
  "origin": "未知",          // 诚实（知识库未标注产地）
  "confidence": 0.75,        // 降低（因为信息不完整）
  "reasoning": "分类来自知识库定义，口味来自商品名称，包装、含糖属性、功能、产地信息在知识库中未找到明确依据，输出为"未知""
}
```

## 问题根源

### 1. **LLM幻觉（Hallucination）**
大型语言模型（LLM）在面对不确定的问题时，会倾向于生成看似合理但实际错误的信息。这种现象被称为"幻觉"。

**示例**：
- 模型不知道NFC橙汁的具体包装 → 瞎猜"纸盒"
- 模型不知道产地 → 瞎猜"全国"

### 2. **知识库信息不完整**
当前知识库存在以下信息缺失：

| 字段 | 缺失情况 | 影响 |
|------|---------|------|
| **口味** | 仅有分类级别的口味描述 | 无法确定具体商品口味 |
| **包装** | 部分分类缺失 | 无法确定具体包装形式 |
| **含糖属性** | 大部分分类缺失 | 无法判断含糖/无糖 |
| **功能** | 部分分类缺失 | 无法提取功能描述 |
| **产地** | 基本缺失 | 完全无法判断 |

### 3. **提示词设计不当**
之前的提示词过于强调"全面性"，鼓励模型填充所有字段，导致模型倾向于编造信息。

## 解决方案

### ✅ **方案1：严格提示词（已实施）**

**改进措施**：
1. 明确要求**只输出知识库中明确提供的信息**
2. 对于不确定信息，**必须输出"未知"**
3. **禁止使用模糊词汇**（"全国"、"常见"、"通常"等）
4. 要求在`reasoning`字段中说明每个判断的依据

**提示词改进**：
```python
重要原则：
- 只输出知识库中明确提供的信息
- 对于知识库中没有的信息，必须输出"未知"，禁止编造
- 任何字段都不能随意填写，必须有据可查
```

### 📊 **方案2：信息完整度评估**

**评估维度**：

| 完整度等级 | 置信度 | 说明 |
|-----------|--------|------|
| **高完整度** | 0.9-1.0 | 商品名称包含品牌+口味+规格，知识库信息完整 |
| **中等完整度** | 0.7-0.9 | 分类准确，部分属性可推断 |
| **低完整度** | 0.5-0.7 | 分类准确，但大部分属性为"未知" |
| **不确定** | < 0.5 | 分类本身不确定，属性信息缺失严重 |

**置信度计算**：
```python
confidence = (
    分类准确度 × 0.4 +
    品牌识别度 × 0.2 +
    口味识别度 × 0.15 +
    包装识别度 × 0.1 +
    含糖识别度 × 0.05 +
    功能识别度 × 0.05 +
    产地识别度 × 0.05
)
```

### 🛠️ **方案3：知识库增强**

**短期措施**（快速提升）：
1. 完善**口味字段**：为每个分类补充完整的口味列表
2. 补充**含糖属性**：为常见品类标注含糖/无糖
3. 规范**包装类型**：统一包装类型的表述

**长期措施**（持续优化）：
1. 建立**商品主数据（Master Data）**系统
2. 接入**官方商品数据库**（如：品牌官网、电商平台）
3. 定期**人工审核和补全**缺失信息

### 🔍 **方案4：多源验证**

**交叉验证逻辑**：
```python
def validate_information(product_name, context, extracted_info):
    validated_info = {}
    
    # 1. 商品名称验证
    if "可口可乐" in product_name:
        validated_info["brand"] = "可口可乐"  # 信任
    else:
        validated_info["brand"] = "未知"  # 降级
    
    # 2. 知识库验证
    if extracted_info["packaging"] in context["all_packagings"]:
        validated_info["packaging"] = extracted_info["packaging"]  # 信任
    else:
        validated_info["packaging"] = "未知"  # 降级
    
    # 3. 一致性验证
    if extracted_info["sugar_content"] != "未知":
        # 检查是否与口味矛盾（如："无糖可乐"）
        if "无糖" in product_name and extracted_info["sugar_content"] == "含糖":
            validated_info["sugar_content"] = "无糖"  # 纠正
        else:
            validated_info["sugar_content"] = extracted_info["sugar_content"]
    else:
        validated_info["sugar_content"] = "未知"
    
    return validated_info
```

## 用户指南

### 如何识别不可靠的输出？

**检查方法**：

1. **查看置信度**
   - `confidence > 0.8` → 信息相对可靠
   - `confidence 0.5-0.8` → 部分信息可能为"未知"
   - `confidence < 0.5` → 大部分信息不可靠

2. **检查"未知"字段**
   - 如果多个字段为"未知"，说明知识库信息不完整
   - 不要依赖这些"未知"字段进行业务决策

3. **阅读reasoning字段**
   - 好的reasoning应该明确说明每个判断的依据
   - 如果reasoning模糊或缺失，说明信息可靠性低

4. **交叉验证**
   - 使用多个商品名称测试，看结果是否一致
   - 对比不同时间的输出，检查稳定性

### 如何提高输出准确性？

**技巧**：

1. **使用完整的商品名称**
   ```
   ✅ 好："可口可乐330ml罐装"
   ❌ 差："可口可乐"
   ```

2. **包含品牌信息**
   ```
   ✅ 好："农夫山泉NFC橙汁1L"
   ❌ 差："NFC橙汁1L"
   ```

3. **包含口味描述**
   ```
   ✅ 好："元气森林白桃味气泡水"
   ❌ 差："元气森林气泡水"
   ```

4. **避免模糊名称**
   ```
   ❌ 差："饮料"
   ✅ 好："可口可乐330ml罐装"
   ```

## 总结

### 核心原则
1. **诚实**：只输出已知信息，"未知"比"瞎编"好
2. **透明**：明确标注信息完整度和置信度
3. **可追溯**：说明每个判断的依据

### 改进承诺
- ✅ 已实施严格提示词，禁止编造信息
- ⏳ 完善置信度评估体系（第2周）
- ⏳ 补全知识库信息（第3-4周）
- ⏳ 建立多源验证机制（持续）

### 用户行动建议
1. 优先使用高置信度（> 0.8）的输出
2. 关注"未知"字段，不要依赖缺失信息
3. 阅读reasoning字段了解判断依据
4. 提供反馈帮助持续优化系统
